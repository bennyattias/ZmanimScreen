# Zmanim Screen — Documentation

A wall-mounted display showing zmanim, the daily daf, the weekly parasha, a Hebrew/civil calendar, weather, and a family photo — running on a Raspberry Pi connected to a monitor.

---

## 1. Setting up the Pi

**What you'll need:** a Raspberry Pi (3, 4, or 5 recommended), a microSD card (8GB+), a monitor with an HDMI input, the correct HDMI-to-micro-HDMI (Pi 4/5) or HDMI-to-mini-HDMI (Pi 3) cable for your specific Pi model, a USB-C power supply, and a computer to flash the SD card from.

1. Download **Raspberry Pi Imager** from [raspberrypi.com/software](https://www.raspberrypi.com/software/).
2. Open Imager and select the OS image: choose **Raspberry Pi OS (64-bit)** — the full **Desktop** version, not "Lite." Lite has no graphical display, which this project needs in order to show a browser on the monitor.
3. Click the gear/settings icon (or "Edit Settings" in newer Imager versions) to configure the Pi *before* flashing — this saves a step later:
   - Set a hostname (e.g. `zmanim`), so you can reach the Pi at `zmanim.local` instead of hunting for its IP address.
   - Set a username/password.
   - Enable SSH (recommended — lets you transfer files and manage the Pi remotely without needing a keyboard permanently attached).
   - Optionally pre-configure Wi-Fi so it connects automatically on first boot.
4. Insert the microSD card, select it as the target storage device, and start the write. Imager will flash and verify the card.
5. Once complete, insert the microSD card into the Pi, connect the Pi to the monitor via HDMI, and power it on with the USB-C supply.
6. On first boot, follow the on-screen setup wizard (if you didn't pre-configure everything in step 3) — country/locale, Wi-Fi, and any pending updates.

## 2. Setting up the app

### Getting the files onto the Pi

Once the Pi is booted and on your network, transfer the project files (`index.html`, `styles.css`, `app.js`, `server.js`, and the `images/` folder) onto it. **Do not** write these files directly to the SD card from your computer via a card reader — the Pi's Linux filesystem isn't natively writable from Windows/Mac that way. There are a few ways to get the files across instead — pick whichever fits your situation.

#### Option A: SCP over SSH (simplest, if your network allows it)

> **Run on:** your computer (not the Pi), from the folder that contains your local copy of the project files — `scp` reads `./zmanim-project` as a path on your machine and pushes it to the Pi.

```bash
scp -r ./zmanim-project pi@zmanim.local:/home/pi/zmanim
```

(Replace `zmanim.local` with your Pi's actual hostname or IP, and `pi` with your actual Pi username — check both with `hostname` and `whoami` on the Pi if unsure, since these vary depending on what you set during Imager setup.)

**If this times out or says "destination host unreachable"** even though the Pi is powered on and connected: this is usually **AP/client isolation** — a setting on some routers (especially guest networks, mesh systems, or IoT-segmented setups) that prevents devices on the same Wi-Fi from talking to each other directly, even though both have valid IPs on the same subnet. You can confirm this by running `ping <pi-ip>` from your computer and `ping <your-computer-ip>` from the Pi — if both fail with "unreachable" while each device's own network config looks correct, isolation is the likely cause. If you don't have router access to disable it, use Option B or C instead.

#### Option B: GitHub (works even with network isolation, since both devices just need internet access, not each other)

On your computer, push the project to a GitHub repo (private is fine). Then on the Pi:

```bash
git clone https://github.com/yourusername/ZmanimScreen.git /home/.../ZmanimScreen
```

**For a private repo**, GitHub will prompt for a username and password — but it no longer accepts your actual account password for git operations. Use a **Personal Access Token** instead:
1. On GitHub (in a browser): **Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token**, with the `repo` scope checked.
2. Copy the token immediately (it's only shown once).
3. When `git clone` prompts for a password, paste the token instead.

To avoid re-entering the token on every future `git pull`, have git remember it on the Pi:
```bash
git config --global credential.helper store
```

For future updates, `git pull` from inside the project folder replaces the file entirely each time — see [§6](#6-updating-the-app).

Add a `.gitignore` before your first push so personal/local-only files don't end up in the repo:
```
settings.json
images/family-photo.*
.idea/
node_modules/
.DS_Store
Thumbs.db
```
(`settings.json` and the uploaded photo are generated by the server itself and shouldn't be overwritten by a `git pull` — see the note in [§6](#6-updating-the-app).)

#### Option C: USB drive (most reliable if neither of the above works)

1. Copy your project folder onto a USB flash drive from your computer.
2. Plug the drive into one of the Pi's USB ports.
3. On the Pi's terminal, copy from the drive into your project folder:
   ```bash
   cp -r /media/<your-username>/<drive-name>/ZmanimScreen /home/<your-username>/ZmanimScreen
   ```
   Run `ls /media/<your-username>/` first if you're not sure what the drive's mount name is.

This works regardless of any network issue, but means manually re-copying the drive for every future update rather than a single command.

### Installing Node.js

SSH into the Pi, or open a terminal directly on it:

> **Run on:** your computer, to open a connection to the Pi. Directory doesn't matter.

```bash
ssh pi@zmanim.local
```

Install Node.js (this pulls in `npm` as well):

> **Run on:** the Pi (you're now inside the SSH session, or in a terminal opened directly on the Pi — either works identically for this). Directory doesn't matter — these install system-wide.

```bash
sudo apt update
sudo apt install -y nodejs npm
```

Confirm it installed correctly:

```bash
node -v
```

No other packages need to be installed — this app has **zero npm dependencies**. It's built entirely on Node's built-in `http`, `fs`, and `path` modules, so there's no `npm install` step for the app itself.

### Running the server

> **Run on:** the Pi — SSH is fine for this. **Directory:** must be run from inside the project folder — `cd` there first, since `server.js` expects `settings.json` and `images/` to be alongside it.

```bash
cd /home/pi/zmanim
node server.js
```

You should see `Running on port 8000` in the terminal. Leave this running, or see [§5 Running automatically on boot](#5-running-automatically-on-boot) to avoid needing to start it by hand every time.

### Launching the display

Open a second terminal (or terminal tab) on the Pi itself — this step needs the Pi's own graphical session, so it can't be done purely over SSH — and launch the browser in kiosk mode, pointed at the server you just started:

> **Run on:** the Pi — but this one specifically needs a terminal opened within the Pi's own desktop session, not an SSH connection. Unlike the other "run on the Pi" commands in this doc, SSH doesn't work here: kiosk mode needs to open a window on an active display, and a standard SSH session has no connection to the Pi's screen. Directory doesn't matter.

```bash
chromium --noerrdialogs --disable-infobars --kiosk --password-store=basic http://localhost:8000
```

(If that command isn't found, try `chromium-browser` instead of `chromium` — the binary name varies slightly by OS version.)

This opens the page full-screen with no address bar or browser chrome. See [§5](#5-running-automatically-on-boot) to make this happen automatically on every boot instead of manually each time.

## 3. Setting preferences

Click the gear icon in the bottom-right corner of the screen to open the settings panel. From there you can change:

| Setting | What it affects                                                                                         |
|---|---------------------------------------------------------------------------------------------------------|
| **Mishpachas word** (Hebrew) | The first word in the header (e.g. "משפחת")                                                             |
| **Family name** (Hebrew) | The second word in the header (e.g. "אטיאס")                                                            |
| **Zip code** | Location used for weather, zmanim, and the Hebrew calendar zmanim                                       |
| **Minutes after shkiah for havdalah** | Havdalah calculation offset, applied both in the parasha box and the calendar's Shabbos/holiday entries |
| **Family photo** | Uploads a new photo for the center display; automatically resized/compressed before upload              |

Changes save immediately — the display refreshes itself within a few seconds without needing a manual page reload. A small status message near the Save button confirms success or reports any error (e.g. an invalid zip code).

## 4. Architecture

### Files

```
index.html                 — page structure, calendar widget setup (FullCalendar)
styles.css                 — all visual styling
app.js                — client-side logic: fetching data, rendering, clock, settings modal
server.js                    — Node server: caches external API data, serves files, handles settings/photo uploads
settings.json              — persisted user preferences (auto-created/updated by the server)
images/
  background.jpg           — page background texture
  sample-family-photo.png  — default photo shown before any upload
  settings-icon.png        — gear icon for the settings button
  family-photo.<ext>       — the currently uploaded family photo, created after first upload
```

### Frontend / Backend split

- **Frontend:** plain HTML, CSS, and vanilla JavaScript — no build step, no framework. FullCalendar (loaded via CDN) renders the Hebrew/civil calendar.
- **Backend:** a single-file Node.js server (`server.js`) using only built-in modules (`http`, `fs`, `path`) — no Express, no npm dependencies. It fetches from external Jewish-calendar and weather APIs, caches the results in memory, and serves both the static files and a small JSON API to the frontend.

### Data flow

```
Browser                           Node (server.js)              External APIs
  |                                |                               |
  |-- GET / ---------------------->|                               |
  |<-- index.html -----------------|                               |
  |-- GET /styles.css ------------>|                               |
  |<-- styles.css -----------------|                               |
  |-- GET /app.js ----------->     |                               |
  |<-- app.js ---------------------|                               |
  |                                |                               |
  |  (app.js runs, fetches)        |                               |
  |-- GET /api/data -------------->|                               |
  |                                |-reads from in-memory cache--->|
  |<-- JSON (parasha, daf yomi,    |   (see caching note below)    |
  |     zmanim, weather, etc.) ----|                               |
  |                                |                               |
  |  app.js updates the DOM        |                               |
  |  Page is fully rendered        |                               |
```

### Caching strategy

`/api/data` never makes a live external call while responding to the browser — it always reads from data the server already fetched and cached in memory, so responses are instant regardless of how slow or unreliable an external API might be at that moment.

- **Parasha, daf yomi, hebrew date, zmanim, Shabbos times** — refreshed once every 24 hours, timed to just after midnight.
- **Weather** — refreshed every 15 minutes, since it's the only piece of data that meaningfully changes within a single day.
- **On any fetch failure**, the server keeps serving the last known-good data rather than showing a blank/broken screen, and retries automatically on the next scheduled refresh.
- **Changing settings** (zip, havdalah minutes) triggers an immediate background refresh rather than waiting for the next scheduled cycle, so changes show up within a few seconds instead of up to a day later.

External services used: **Hebcal** (zmanim, daf yomi, parasha, Hebrew date, Shabbos times, holiday calendar) and **Open-Meteo** (weather).

## 5. Running automatically on boot

To avoid manually starting the server and launching kiosk mode after every reboot or power cycle. All steps in this section run **on the Pi**.

**Auto-start the server** — create a `systemd` service so it starts on boot and restarts itself if it ever crashes:

> **Run on:** the Pi — SSH is fine for this. Directory doesn't matter — you're editing an absolute path.

```bash
sudo nano /etc/systemd/system/zmanim.service
```

```ini
[Unit]
Description=Zmanim Screen Server
After=network.target

[Service]
ExecStart=/usr/bin/node /home/pi/zmanim/server.js
WorkingDirectory=/home/pi/zmanim
Restart=always
User=pi

[Install]
WantedBy=multi-user.target
```

Enable it:

> **Run on:** the Pi — SSH is fine for this. Directory doesn't matter.

```bash
sudo systemctl enable zmanim.service
sudo systemctl start zmanim.service
```

**Auto-launch the browser in kiosk mode** — create an autostart entry:

> **Run on:** the Pi — SSH is fine for *creating* this file, since `nano` doesn't care whether you're local or remote, and triggering a reboot afterward (`sudo reboot`) is equally fine over SSH. What SSH *can't* do is show you the result: the file is read by the desktop session at the next login/boot, and confirming it actually launched Chromium in kiosk mode means looking at the physical monitor — an SSH session ends the moment the Pi reboots, so there's nothing left to check from it. Directory: your home folder (`~`) — no need to `cd` anywhere else first.

```bash
mkdir -p ~/.config/autostart
nano ~/.config/autostart/kiosk.desktop
```

```ini
[Desktop Entry]
Type=Application
Name=Zmanim Kiosk
Exec=chromium --noerrdialogs --disable-infobars --kiosk --disable-session-crashed-bubble --password-store=basic http://localhost:8000
X-GNOME-Autostart-enabled=true
```

**Disable screen blanking** — since there's no keyboard/mouse activity to keep the display awake, add these lines to the same autostart process (or a small startup script run before Chromium launches). These also need the Pi's own graphical session to have any effect, same as the kiosk entry above:

```bash
xset s off
xset -dpms
xset s noblank
```

## 6. Updating the app

**If you transferred the files via SCP (Option A):** deploy a new version of any file after making changes on your computer:

> **Run on:** your computer (not the Pi), from the folder containing your local, edited copy of the file — `scp` sends `app.js` as it exists on your machine.

```bash
scp app.js pi@zmanim.local:/home/pi/zmanim/app.js
```

(Repeat for whichever files changed — `server.js`, `index.html`, `styles.css`.)

**If you cloned the files via GitHub (Option B):** push your changes to the repo from your computer as usual, then pull them down on the Pi:

> **Run on:** the Pi — SSH is fine for this. **Directory:** must be run from inside the project folder.

```bash
cd /home/.../ZmanimScreen
git pull
```

This is why `settings.json` and the uploaded photo (`images/family-photo.*`) are in `.gitignore` — if they were tracked, a `git pull` would overwrite whatever zip code, family name, or photo you'd set through the live settings panel with whatever was last pushed from your dev machine, silently resetting your actual configured preferences on every update.

**Either way**, if `server.js` changed, restart the server for the change to take effect:

> **Run on:** the Pi — SSH is fine for this. Directory doesn't matter.

```bash
sudo systemctl restart zmanim.service
```

Frontend-only changes (`index.html`, `styles.css`, `app.js`) just need the browser to reload — either restart the kiosk browser process, or reboot the Pi.

## 7. Troubleshooting

| Symptom | Likely cause |
|---|---|
| Blank screen after boot | Chromium launched before the Node server was ready. Confirm `systemctl status zmanim.service` shows it running, then restart Chromium. |
| Weather/zmanim stuck on old data | Check server logs (`journalctl -u zmanim.service -f`) for repeated fetch failures — the server keeps last-known-good data automatically, so this usually means an extended outage of Hebcal or Open-Meteo, not a bug. |
| Settings save seems slow | The server responds as soon as settings are saved; zip/havdalah-dependent data refreshes in the background over the next few seconds. |
| Uploaded photo doesn't appear | Confirm the `images/` folder is writable by the user running the server (`ls -la images/`). |
| Calendar still shows old candle-lighting times after changing zip | Should self-correct within a few seconds — the calendar explicitly re-fetches after a settings save. |
| `scp`/`ssh` times out or says "destination host unreachable," even though the Pi is on and its IP is confirmed correct | Likely AP/client isolation on the router — a setting that blocks devices on the same Wi-Fi from reaching each other directly. Confirm with `ping` in both directions; if both fail, use the GitHub or USB transfer method instead (see [§2](#2-setting-up-the-app)). |
| `git clone`/`git pull` says authentication failed | GitHub no longer accepts your account password for git — use a Personal Access Token in its place when prompted for a password (see [§2, Option B](#2-setting-up-the-app)). |
